# Execution evidence and timing diagnostics

This change adds observation, not new trading rules. Entry sizing, admission,
fill prices, exit rules and cash calculations are unchanged. No broker API is added.

## Durable linkage (schema 2)

- New BUY fills save `positions.entry_order_id` in the same transaction as the
  position and cash update. Normal position updates preserve it.
- Model SELL, stop, target, time and margin exits copy this ID to the trade in
  the same transaction as the close. A rollback cannot leave half a linkage.
- Stock, crypto and Taiwan admission diagnostics include order and decision IDs.
- Existing rows receive NULL. There is deliberately **no guessed backfill**.
- The read-only audit checks the entry decision, gate, order, position/trade,
  timestamps, price/quantity/notional and recorded realized P&L. Model exits also
  check their SELL order. Protective exits legitimately have no SELL order.
- A missing post-fill diagnostic, old schema or limited diagnostic window can
  leave a real trade UNRESOLVED; this is missing proof, not automatic corruption.
- VALIDATED_OPEN is not full round-trip validation. Only VALIDATED_CLOSED is.

`research_snapshot.execution_audit` is produced in one read transaction with
query-only mode, explicit close and a cooperative 8-second SQL/Python budget
(SQLite busy wait bounded to 1 second). Up to 200 recent BUY orders and 5000
admission diagnostics are examined. Limits and row counts are public. It is not
an all-history validation. Errors return ERROR, never an empty successful audit.

## Loss attribution

The snapshot groups all recorded closed trades by account, account/strategy,
account/symbol and account/exit reason; each table exposes the 50 lowest-P&L
groups. These are descriptive concentrations, not proof of causation.
Cost-adjusted entry/exit prices already affect realized P&L, so order fees and
slippage must not be deducted again. Financing and unrealized P&L are excluded.
Do not call this daily return or combine accounts with different quote currencies.

The V9 dashboard displays this evidence from the exported JSON, not by querying
or modifying the ledger. Missing or stale evidence is explicitly labelled.

## Timing

Both dashboards and public worker feeds expose the 10 slowest completed asset/
horizon tasks in the current and previous cycle (wall seconds and bars processed)
and the last 20 completed/failed cycles. History is in memory and resets on worker
restart. No market query or new work event is generated by reading this history.
Phase timings remain separate. These observations identify where time is spent;
they do not prove why a cache, database or model operation is slow.

The snapshot sync allowlist now preserves in-flight backup progress separately
from the last completed backup. Push-triggered sync is restricted to main so a
feature-branch push cannot publish production snapshots.

## Release and rollback gate

This branch is **not authorization to deploy**. Before deployment capture a fresh,
verified consistent backup using the existing maintenance procedure and confirm
disk headroom. Schema migration adds nullable columns and indexes, retaining rows
and balances. Old schema-1 code rejects user_version=2: do not blindly redeploy an
old image or restore a predeployment ledger over new trades. Prefer a forward fix;
any rollback requires a reviewed compatibility/data-preservation plan.
The concrete [schema-2-compatible recovery plan](schema2_recovery.md) retains the
new DB adapter with the pinned PR22 runtime. A separate CI job tests that exact
runtime/adapter combination. It is not an authorization to deploy or an automatic
restore procedure; the fresh maintenance backup gate still applies.

After deployment, confirm updated snapshot timestamps and worker cycles, eight
restored databases, successful seven-database backup plus independent V10 backup,
zero broker calls, and new linked admission samples. Legacy NULL links must remain
visible as UNRESOLVED; never relax the gate to manufacture validation samples.
